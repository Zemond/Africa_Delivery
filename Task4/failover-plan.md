# План отказоустойчивости и переключения (Failover Plan)

Цель: пережить отказ/отключение дата-центра без потери данных сверх RPO и с восстановлением в пределах RTO.

## Стратегия высокой доступности

- Активный регион: AWS af-south-1 (ЮАР/Кения) + локальный нигерийский провайдер (Нигерия).
- Резерв: GCP africa-south1 как тёплый standby для сервисов и данных (pilot-light: минимальный рантайм, данные реплицируются).
- Репликация: PostgreSQL — streaming replication; объектное хранилище — cross-region replication; нигерийские данные — в пределах Нигерии (не выносим без заключения юриста).
- RTO / RPO: RTO ≤ 4 часа, RPO ≤ 15 минут (NFR-06, NFR-07).

## Сценарии отказа

### Сценарий 1: отказ AWS af-south-1 (ЮАР/Кения)

- Кто решает: дежурный SRE + Solution Architect; эскалация CEO/CFO при > 30 минут.
- Шаги: 1) зафиксировать отказ и объявить Sev-1; 2) переключить DNS/трафик на GCP africa-south1; 3) поднять сервисы из standby; 4) промоутировать реплику БД; 5) проверить каталог/заказы/оплату; 6) уведомить стейкхолдеров.
- Время: ≤ 4 часа.
- Потери данных: ≤ 15 минут (RPO), заказы в полёте — повторная обработка через очередь.

### Сценарий 2: отказ локального нигерийского провайдера

- Кто решает: дежурный SRE + юрист (для оценки допустимости временного выноса данных).
- Шаги: 1) объявить Sev-1; 2) переключить нигерийский трафик на standby-инстанс у того же или резервного локального провайдера; 3) восстановить БД из реплики; 4) не выносить персональные данные за границу без подтверждения юриста; 5) при длительном отказе — режим деградации (приём заказов с минимумом данных).
- Время: ≤ 4 часа (при наличии резервного локального провайдера).
- Потери данных: ≤ 15 минут.

### Сценарий 3: отказ платёжного провайдера (M-Pesa)

- Кто решает: дежурный + Backend.
- Шаги: Circuit Breaker уже разомкнут → включить fallback на Flutterwave/карту; уведомить пользователей; сверка после восстановления.
- Время: немедленно (автоматически).
- Потери данных: нет, заказы сохраняются.

### Сценарий 4: полная потеря региона (катастрофа)

- Кто решает: Solution Architect + CEO (решение о DR-активации).
- Шаги: 1) активировать DR-процедуру; 2) восстановить из бэкапов в резервном регионе; 3) валидировать целостность; 4) пошаговый ввод трафика.
- Время: ≤ 24 часа (вне штатного RTO, катастрофа).
- Потери данных: до последней репликации/бэкапа (≤ 15 минут при рабочей репликации).

## Роли и дежурство

- Дежурный SRE — первичная реакция, диагностика, эскалация.
- Solution Architect / Deputy CTO — решение о переключении региона.
- CFO/CEO — уведомление при инцидентах уровня Sev-1 (деньги/долгий простой).
- Юрист — консультация при любом сценарии, затрагивающем границу данных.

## Проверка

Учения по failover проводятся до запуска (минимум один прогон сценария 1) и далее ежеквартально.
