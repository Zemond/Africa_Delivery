## 2. Движение данных между странами (что и через что проходит)

Общего шлюза в af-south-1 для Нигерии и Кении больше нет. У каждой страны свой вход (ingress + API gateway) и свой инстанс приложения (`Task4/failover-plan.md`). Запрос нигерийского покупателя от телефона до базы проходит только по Нигерии, кенийского — только по Кении. Переключение при отказе тоже идёт на резервную площадку внутри той же страны.

Между странами ходят только:

1. Публичный каталог (товары, цены, медиа) — из первичной копии в af-south-1 в read-реплики Нигерии и Кении и в CDN. Это не персональные данные.
2. Serving-копия профилей кенийцев — из первичной копии в af-south-1 в Кению (требование KICA о копии в юрисдикции).
3. Агрегированные метрики без идентификаторов пользователей (число запросов, задержки, ошибки по стране) — в общий Grafana.

Технические поля запроса проверены на персональные данные:

- `session_token` — непрозрачная случайная строка (256 бит), а не JWT с данными. Сессия хранится в Redis страны субъекта; по токену нельзя восстановить телефон, имя или страну.
- Если между сервисами нужен JWT, в claims только псевдонимный `sub` (UUID, не телефон), `country`, `scope` и `exp` — без телефона, имени, email и адреса.
- `request_id` и `trace_id` — случайные (UUIDv4 / W3C Trace Context), они не выводятся из телефона, номера заказа или ID пользователя. Baggage OpenTelemetry не несёт атрибутов пользователя.
- Телефон, email и адрес не передаются в URL и query string — только в теле запроса по TLS. Поэтому они не попадают в access-логи входа и CDN.
- Логи: тела запросов не пишутся; OTel Collector страны маскирует телефон, email, имя, адрес и номер карты и удаляет заголовки `Authorization`/`Cookie`. Нигерийские логи и трейсы хранятся в Нигерии (`Task3/observability.md`).

Где лежат копии:

- Нигерийские персональные данные — только внутри Нигерии, реплика для DR тоже внутри страны (ЦОД-2 у второго локального провайдера). За границу не выносятся — ни копией, ни транзитом через чужой шлюз.
- Кенийские профили — первичная копия в af-south-1 + serving-копия в Кении (требование KICA о хранении копии в юрисдикции). Платёжные данные и заказы кенийцев — первично в Кении, реплика — на площадке-2 в Кении.
- Южноафриканские — af-south-1 (это и есть территория ЮАР), реплика — GCP africa-south1 (тоже ЮАР).
- Логи и аудит — в стране площадки, для Нигерии — только в Нигерии. Это технический журнал без персональных данных в открытом виде.

Что останется в стране при отказе региона:

- При отказе af-south-1 (ЮАР): Нигерия и Кения продолжают обслуживаться автоматически через свои входы — их запросы и раньше не шли через af-south-1. Каталог читается из локальных реплик (новые товары появятся после переключения ЮАР-контура на GCP africa-south1), правки профилей кенийцев копятся в очереди в Кении. Отказ расходует бюджет ошибок ЮАР (до 15 минут), а не выводится за пределы SLO.
- При отказе нигерийского провайдера: GSLB переключает трафик на ЦОД-2 у второго локального провайдера в Нигерии, данные за границу не выносятся. Если недоступны обе площадки — режим деградации (статическая витрина каталога из CDN, приём заказов приостановлен); временный вынос данных — только с подтверждения юриста.

## 3. Принципы

1. Нигерийские персональные данные — только в Нигерии. У AWS/Google/Microsoft нет региона в Нигерии, поэтому используем локального провайдера. Это консервативное допущение до заключения юриста (артефакт 3).
2. Псевдонимизация не отменяет локализацию до письменного подтверждения юриста. Для Нигерии псевдонимизированные заказы пока держим тоже в стране — это консервативный выбор, который мы сможем ослабить, если юрист разрешит вынос.
3. Шифрование — мера поверх локализации, а не её замена.
4. Обратимость: граница данных задана policy, а не кодом, чтобы после ответа юриста перенести категорию данных без переписывания (ADR-003).
5. Общего шлюза нет: у каждой страны свой вход, поэтому персональные данные не покидают страну даже транзитом. В токенах, идентификаторах запросов и логах персональных данных в открытом виде нет.
